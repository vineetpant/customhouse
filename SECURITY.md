# Security

Penstock is a security tool, so it owes you a precise account of what it does
and does not defend against. This document is that account. `DESIGN-v2.md` holds
the full threat model; this is the operator-facing summary, kept honest.

**Applies to:** v0.2.0. Pre-1.0 and not yet production-hardened.

## What Penstock enforces today

| Property | Mechanism |
| --- | --- |
| **Untrusted input cannot reach a money-moving or data-egress tool** | Every upstream carries a trust class. The moment an untrusted server's result enters the session, the session is tainted; sink calls are then refused — including sinks on a *different* upstream — with the causing server and call named |
| An upstream cannot silently change a tool's definition | Definitions are pinned at first sight; a changed definition is **withheld** — never served — until an operator runs `penstock repin <server>` |
| A mediated call cannot reach Penstock's own files | Compiled-in invariants deny any call whose path-like argument resolves into the Penstock home directory, the binary, or the active config |
| The audit trail cannot be read or edited through the proxy | The ledger is append-only and lives inside the protected home directory |
| Enforcement is deterministic | No model call, no network access, and no nondeterminism anywhere in the decision path |

Every property is demonstrated by a runnable script that asserts it and fails
loudly if it regresses: `./demo/run_flow_block.sh`, `./demo/run.sh`,
`./demo/run_rugpull.sh`, `./demo/run_selfprotect_real.sh`.

Measured behaviour is published in [`METRICS.md`](./METRICS.md) — block rate and
false-positive rate, side by side, regenerated by `./demo/run_metrics.sh`.

## Not implemented yet

- **Capability profiles** (R2) — per-server network/filesystem/exec confinement.
- **Mediation beyond tools.** Only `tools/call` and `tools/list` are mediated.
  Resources and prompts are explicitly **refused** rather than silently passed;
  sampling, Tasks and MCP Apps are not handled.
- **Value fingerprinting.** Flow decisions are session-scoped only. Penstock does
  not yet distinguish "this sink call literally contains bytes from the untrusted
  read" from "this session merely saw untrusted content".
- **Signed audit records.** The ledger is plain JSONL: anyone who can write the
  file can forge or truncate it. It is evidence for an operator, not proof
  against a determined adversary with disk access.

## Known limitations (by design, not bugs)

These are structural. They are not scheduled to be "fixed", because the fix
belongs at a different layer or does not exist at this boundary.

### Flow enforcement is session-scoped, and that is a real limit

Penstock sits at the tool boundary. It can see what entered the model's context
and what the model asked for next — but nothing about how the model combined
them. Per-variable information flow is not observable from here, and claiming it
would be false.

So the rule is coarse: once *any* untrusted content enters a session, *every*
sink call in that session is refused. Two consequences follow, and both are
measured rather than argued:

- **It over-blocks.** A legitimate workflow that reads an untrusted source and
  then uses a sink — reading a support ticket and replying to it, fetching a page
  and posting a summary — is blocked. The measured false-positive rate is **40%**
  across benign workflows that use sinks (see [`METRICS.md`](./METRICS.md)). That
  is why `external_send` and `data_egress` are recommended to run in
  `require_approval` rather than `deny`.
- **It cannot be evaded by transformation.** Because no content is ever
  inspected, summarising, translating, re-encoding or paraphrasing the untrusted
  data does not help an attacker. The guarantee is about provenance, not text.

The trade is deliberate: a rule that is coarse but unevadable, over one that is
precise but defeated by base64.

### Taint ordering assumes a sequential client

The taint from call *N* must be visible when call *N+1* is judged. Penstock
serialises mediated calls to guarantee this, but a client that dispatches
several requests *simultaneously* can still have a sink evaluated before an
in-flight untrusted read has landed.

Real agents are sequential — a model cannot choose its next call before seeing
the previous result — so this requires a client that is deliberately pipelining,
which is the malicious-client case already out of scope. It is recorded here
because it is a real property of the implementation, not because it is
comfortable.

### Trust classification is the operator's judgement

Penstock enforces the flow rule; it does not decide which servers are
trustworthy. An upstream marked `trusted` never taints anything, so mislabelling
a server that returns attacker-influenced content silently disables the
protection for that path. Unlisted servers default to `untrusted`, so the
failure mode of forgetting is safe; the failure mode of asserting wrongly is not.

### Path checks are advisory: inode aliases and TOCTOU

Self-protection identifies protected files **by path**. Canonicalization resolves
symlinks, `..`, and `~`, but two things escape it:

- **Inode aliases.** A hardlink to a protected file, or a bind mount of the
  Penstock home, is a *second real name* for the same data. It resolves outside
  every protected root, so it is allowed, and reading it returns the protected
  file's contents.
- **Time-of-check/time-of-use.** Penstock checks a path and then forwards the
  call; the *upstream server* opens the file moments later. The filesystem can
  change in between.

Checking `(st_dev, st_ino)` instead of paths would not close either hole:
not-yet-existing targets have no inode (and denying writes to files that do not
exist yet is required), and TOCTOU is unfixable by any component that does not
itself hold the file descriptor.

**Why this is acceptable:** creating such an alias *through a mediated call* is
itself denied, because the call must name the protected path as its source. So
exploiting this requires filesystem access outside MCP — and an attacker with
that access can simply read the file directly. It grants no capability the
malicious-host case does not already grant.

**Penstock is not a sandbox.** Kernel-level mechanisms (Landlock, Seatbelt,
containers) enforce filesystem confinement atomically and handle aliasing
natively. Pair Penstock with one for hostile-host threat models. As defense in
depth, run Penstock's state under a different OS user than your filesystem
servers.

### Path-like arguments are identified heuristically

An argument is treated as a path if it starts with `~` or contains `/`. This
catches absolute paths, relative paths, traversal, and symlinks — including paths
nested inside arrays and objects. It does **not** catch bare filenames with no
separator, or paths hidden inside encoded or base64 blobs. Per-server argument
schemas (which would remove the guesswork) arrive with capability profiles.

### Metadata pinning is startup-scoped and tools-only

Definitions are checked when Penstock connects to an upstream. A server that
mutates its definitions *mid-session*, without a reconnect, is not currently
re-checked. Pinning also covers tools only — `resources/list` and `prompts/list`
are not pinned, because those surfaces are not yet mediated.

### Out of scope entirely

A malicious client or compromised host OS; attacks that live purely in model
output and never reach a mediated call; semantic laundering, where a model
re-expresses tainted content in its own words (an implicit flow invisible at any
boundary); multi-tenant policy distribution.

## Reporting a vulnerability

Please report privately via GitHub's private vulnerability reporting rather than
a public issue. Findings that show a mediated call reaching Penstock's own state,
a changed tool definition being served without an explicit re-pin, or a sink
call succeeding in a tainted session, are the most valuable — those are the
properties this release actually claims.
