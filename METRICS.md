# Customhouse R3 — measured behaviour

Generated by `./demo/run_metrics.sh`. Scenarios replay through the real flow policy and taint state machine; transport and routing are covered by the demo scripts.

| Metric | Value |
| --- | --- |
| **Block rate** (injection scenarios blocked) | **100%** (12/12) |
| **False-positive rate** (benign sink workflows blocked) | **30%** (3/10) |

## Change since v0.2.1

v0.3.0 added destination classification: a send in a tainted session is allowed when every recipient is the author of the tainted source (DESIGN-v2.md 17).

| | v0.2.1 | v0.3.0 |
| --- | --- | --- |
| Block rate | 100% (11/11) | **100%** (12/12) |
| False-positive rate | 40% (4/10) | **30%** (3/10) |

The block rate held while the attack set *grew* by a scenario: `attacker-address-in-poisoned-body` exercises the inversion that would make this rule a vulnerability, and it is refused. A rule that relaxed enforcement without that scenario passing would not be worth its false-positive saving.

One benign workflow was recovered, `support-reply`. That is the size the reach limit predicts rather than a disappointment: the rule reads authorship from a declared structured field, so it can only help workflows whose sources assert one. Three of the four original false positives do not, or do not send to the author, and are unchanged.

## Post-mortem: the remaining false positives

**On how these scenarios are modelled.** `triage-issue-and-notify` is the one to check if you are reading sceptically. An issue tracker does assert who filed an issue, so the scenario is modelled *with* structured authorship — and it still blocks, because the notification goes to a team channel rather than to the reporter. It fails on `foreign_recipient`, not on missing data. It would have been easy to leave it unauthored and let it fail for want of a field, or to point the notification at the reporter and recover another point of false-positive rate. Neither would reflect the workflow. The suite is modelled on what these systems actually assert, and the number is whatever falls out.

The headline number is easy to misread as "this approach is wrong three times in ten". It is not. In **every** blocked benign workflow, untrusted data genuinely does reach the sink — Customhouse is correct about the flow. What makes these workflows legitimate is not the absence of a flow, it is the *destination*. That diagnosis is what v0.3.0 acted on, and it recovered the one case where the destination is structurally checkable: a reply to the author of the ticket. The rest are below.

That diagnosis ruled out the refinement we had assumed. **Value fingerprinting would have confirmed these blocks rather than cleared them**, because the data really is flowing; finer tracking of a flow tells you nothing when the flow was never the problem. Destination classification was built instead, and it recovered the case it can reach.

What would move the three below is more specific than a general mechanism. Two of them (`summarise-page-to-chat`, `process-uploaded-csv`) read from sources that assert no authorship at all, so no destination check can help; they need either an operator approval or a declared allowlist of internal destinations. The third sends deliberately to a party who did not write the content, which is the shape of an exfiltration and arguably *should* require a human. Fingerprinting still has a use, but the inverted one: fingerprint *trusted* results and refuse author-directed replies that carry them, which closes the residual channel in DESIGN-v2.md 17.6 rather than chasing false positives.

| Workflow | Class | Untrusted data in sink args? | Fingerprinting | Approval as UX |
| --- | --- | --- | --- | --- |
| `summarise-page-to-chat` | `external_send` | Yes semantically; the summary is derived from the page, though reworded. | Might clear it by missing the paraphrase — but that is exactly the transformation an attacker uses, so treating a fingerprint miss as safe would be unsound. | Acceptable. Summarising is deliberate and low-frequency. |
| `process-uploaded-csv` | `data_egress` | Yes — the uploaded artefact is the untrusted data, processed. | Confirms, does not clear. | Acceptable. Batch work, low frequency. |
| `triage-issue-and-notify` | `external_send` | Yes — the notification carries issue text. | Confirms, does not clear. | Borderline. Tolerable at low issue volume, painful at high. |

Read together: session-scoped granularity costs roughly four in ten benign sink workflows an approval prompt. For low-frequency work that is a reasonable price for a guarantee that cannot be evaded by rewording the payload. For high-volume work such as support replies it is not, and the answer there is destination classification rather than a looser rule.
